# План развития: единый layout-экспорт (xlsx/pdf/html из одного описания)

## Цель

Автор описывает отчёт декларативным JSON-layout (блоки: таблица, график, метрика, текст с позицией на сетке). Система сама рендерит его в xlsx, html и pdf (pdf — через html→chromium). Старые `Order`/`Template` конвертируются в layout автоматически при загрузке и удаляются из модели — один кодовый путь.

## Аудит: ключевые факты (обоснование фаз)

- **Экспортер не подключён**: `generator.New` не заполняет поле `exporter` (internal/generator/generator.go:53–79), `exporter.NewEngine` не вызывается нигде → nil-паника на первом отчёте с экспортом.
- **HTML grid-движок уже написан** (internal/exporter/html/layout.go: Grid, размещение first-fit, разрыв таблиц, пагинация), но существует только в HTML; PDF уже идёт через html-экспортер.
- **XLSX — параллельный легаси-путь** по `Order`; `xlsx/layout_definition.go` и `xlsx/charts.go` — пустые заглушки, xlsx-графиков нет.
- **Модели layout нет**: `models.Layout` — пустой struct, `layout.json` — `{}`, в БД нет таблицы; шаблоны привязаны к отчёту веером (report_templates → каждый шаблон джойнится к каждому экспорту, repository/report.go:643–649).
- **Гонки**: глобальный стек коллекторов в html/layout_funcs.go:10 при 4 воркерах генератора; mutable package-global `defaults` в exporter/exporter.go.
- **Прочее**: text-экспортер парсит `format.Format` вместо шаблона (регрессия, text/exporter.go:19); pdf/chromium.go игнорирует свой аргумент shellPath; Taskfile собирает `-tags chromium`, Dockerfile ставит wkhtmltopdf; exporter_test.go закомментирован, example_out.html (8800 строк) закоммичен; тестов grid-движка — ноль.

## Фаза 1 — каноническая модель layout (ядро)

1. **internal/models/layout.go** (вместо пустого export_layout_template.go):
   - `Layout{Version int, Page PageConfig, Blocks []Block}`; `PageConfig{Format:"A4", Orientation, PaddingMM, Header/Footer}`;
   - `Block{ID, Type, Dataset (ссылка на title из Dataset), Pos GridPosition{X,Y,W,H}, Options}` — типизированные варианты: `TableBlock{Columns []Column{Field, Title, Width, Format, Align}, Sort, Limit}`, `ChartBlock{Kind: line|bar|pie, XField, Series []Series{Field,Title,Color}, Stacked}`, `MetricBlock{Field, Label, Format, Delta?}`, `TextBlock{Text (go-template)}` + `RawHTMLBlock` (escape-hatch: html/pdf рендерят как есть, xlsx — текст).
2. **Реестр блоков** (по образцу компонент duckle): `map[BlockType]Definition{Validate, описания опций}` в новом пакете internal/layout (модель в models, логика в internal/layout); валидация `Layout.Validate(datasetKeys)` — известные типы, границы сетки, уникальные ID, существование датасетов.
3. **Автоконвертация легаси**: `LayoutFromOrder(Order map[string][]string)` (таблица на весь лист, лист на датасет) и `LayoutFromTemplate(*Template)` (rich_text/text → TextBlock). Функции в internal/layout + табличные тесты.
4. Пример `internal/models/layout.json` → реальный документ; `sbot config update` / `ctl create` обновить под новую схему.

## Порядок и риски

- Фазы 0→1→2→3 дают вертикаль «JSON-layout → три формата»; каждая фаза — отдельный коммит, система работоспособна после каждой.
- Главные риски: автоконвертация легаси (покрывается табличными тестами в 1.3) и потокобезопасность html-коллектора (фикс в 0.2 обязателен до любых новых рендереров).
- Существующие xlsx-отчёты с Order и text-отчёты с шаблонами продолжают работать через автоконвертацию без правки конфигов пользователей.

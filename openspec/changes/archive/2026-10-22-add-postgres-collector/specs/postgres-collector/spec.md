# Spec Delta

## Purpose

Позволяет собирать данные для отчётов напрямую из Postgres-баз, описанных в конфиге бота, без Metabase. Доступ к этим базам разрешён только на чтение.

## ADDED Requirements

### Requirement: Запрос типа pg
Запрос отчёта с типом `pg` SHALL выполняться в базе, имя которой указано в `card_uuid`. Текст SQL берётся из поля `query` запроса, результат попадает в датасет отчёта под заголовком запроса в виде списка строк «колонка → значение».

#### Scenario: Успешный сбор
- **WHEN** отчёт содержит запрос `pg` с `card_uuid = "analytics"`, `query = "select 1 as x"`, а база `analytics` описана в конфиге
- **THEN** датасет отчёта под заголовком запроса содержит `[{"x": 1}]`

#### Scenario: Неизвестная база
- **WHEN** `card_uuid` запроса `pg` указывает на имя, которого нет в конфиге
- **THEN** сбор этого запроса завершается ошибкой с именем базы, а остальные запросы отчёта собираются как обычно

### Requirement: Подстановка параметров
Значения из `params` запроса `pg` SHALL подставляться в SQL как именованные параметры (`@name`) через биндинг, а не склейкой строк.

#### Scenario: Именованный параметр
- **WHEN** `query = "select @d::date as d"` и `params = {"d": "2026-10-01"}`
- **THEN** результат содержит `d` = 2026-10-01

#### Scenario: Значение не исполняется как SQL
- **WHEN** значение параметра равно `"1; drop table x"`
- **THEN** оно передаётся как значение параметра, и никакая команда, кроме исходного запроса, не выполняется

### Requirement: Только чтение
Коллектор `pg` SHALL выполнять каждый запрос в read-only транзакции и никогда не фиксировать её. Попытка записи или DDL MUST завершаться ошибкой независимо от прав пользователя базы.

#### Scenario: Попытка записи
- **WHEN** `query = "delete from t"` или `"create table t2(x int)"`
- **THEN** запрос завершается ошибкой, данные и схема базы не меняются

#### Scenario: Несколько стейтментов
- **WHEN** `query = "select 1; delete from t"`
- **THEN** запрос завершается ошибкой, `delete` не выполняется

### Requirement: Таймаут запроса
Каждый запрос `pg` SHALL прерываться, если выполняется дольше `statement_timeout`, заданного для этой базы в конфиге.

#### Scenario: Долгий запрос
- **WHEN** `statement_timeout: 1s` и `query = "select pg_sleep(5)"`
- **THEN** запрос завершается ошибкой таймаута примерно через 1 секунду

### Requirement: Конфигурация баз
Базы SHALL описываться в конфиге в секции `databases` как имя → `dsn`, `read_only`, `statement_timeout`, `max_conns`. `read_only` по умолчанию `true` и включает `default_transaction_read_only=on` для всех соединений базы. DSN MUST маскироваться при выводе конфига в лог.

#### Scenario: read_only на соединении
- **WHEN** база описана с `read_only: true` (или без поля)
- **THEN** `show default_transaction_read_only` в соединении коллектора возвращает `on`

#### Scenario: Маскирование DSN
- **WHEN** конфиг выводится в лог
- **THEN** DSN баз из `databases` не отображаются в открытом виде

#### Scenario: База недоступна при старте
- **WHEN** база из конфига недоступна в момент запуска бота
- **THEN** бот стартует, пишет предупреждение, а ошибка возвращается при сборе запроса к этой базе

### Requirement: Доступ из Lua
Lua-скрипты SHALL иметь функцию `collector.pg.collect(db, sql, params)`, которая возвращает строки результата или `nil` и текст ошибки. Ограничения на чтение и таймаут для неё действуют те же.

#### Scenario: Вызов из Lua
- **WHEN** скрипт вызывает `collector.pg.collect("analytics", "select @x::int as x", {x = "5"})`
- **THEN** возвращается таблица `{{x = 5}}` и `nil`

#### Scenario: Запись из Lua
- **WHEN** скрипт вызывает `collector.pg.collect("analytics", "delete from t")`
- **THEN** возвращается `nil` и текст ошибки, данные не меняются

### Requirement: Хранение запроса pg
Запрос `pg` SHALL храниться в БД бота с текстом SQL. Существующий запрос MUST переиспользоваться только при совпадении имени базы, заголовка и текста SQL.

#### Scenario: Разный SQL при одинаковом заголовке
- **WHEN** создаются два отчёта с запросом `pg` к одной базе с одинаковым заголовком, но разным SQL
- **THEN** в БД сохраняются два разных запроса, и каждый отчёт выполняет свой SQL

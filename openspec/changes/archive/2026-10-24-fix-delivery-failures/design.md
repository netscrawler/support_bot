# Design

## Context

- `max.Adaptor.sendUploads` при ошибке `upload` только пишет её в лог и делает `continue`. Любое вложение прикрепляется как `AttachImage`, даже при `UploadFile`.
- `models.Message.sentMax` перезаписывает `sendErr` вместо объединения ошибок и не возвращает сообщение, если на нём была ошибка. Ветка `MaxRecipient` в `Send` при ошибке делает `continue` и теряет уже отправленные сообщения. Поэтому они не удаляются в конце дня.
- `smb.cleanup()` вызывает `smb.cancel()`, то есть отменяет контекст монитора, который `reconnectLoop` передаёт в `connect`. После первого `cleanup` переподключение и сам монитор останавливаются навсегда.
- `smb.write` обращается к `smb.fs` без проверки. После неудачного `cleanup`/`connect` поле равно `nil`, и запись паникует.

## Goals / Non-Goals

**Goals:** закрыть дефекты из proposal и покрыть тестами MAX и SMB.

**Non-Goals:**
- поведение `sendTg` и других каналов;
- гонка по `smb.fs` между монитором и `Upload` (она существовала до ветки, см. Risks);
- перенос диспетчеризации доставки из `models` — это отдельное изменение `refactor-delivery-dispatch`.

## Decisions

1. **Частичная доставка MAX (решение пользователя).** `sendUploads` собирает ошибки через `errors.Join(fmt.Errorf("upload %s: %w", name, err))`. Если есть хоть один токен, сообщение отправляется и возвращается `(msg, uploadErr)`; если токенов нет, возвращается `(nil, uploadErr)`. Альтернативу «любой сбой → не отправлять ничего» пользователь отклонил: получатель должен получить хотя бы то, что загрузилось.
2. **Тип вложения** выбирается по `kind`: `UploadImage → AttachImage`, `UploadFile → AttachFile`.
3. **`sentMax` и `Send`.** `sentMax` добавляет `msg` в результат при любом `msg != nil` и объединяет ошибки через `errors.Join`; заодно исправляется подпись «sending document» у изображений на «sending media». Ветка `MaxRecipient` в `Send` при ошибке сохраняет возвращённые сообщения в `sentMsg` (если `NeedDeleteAfterEndOfDay`), но `delivered` не увеличивает. Тогда запуск станет `failed`/`partial`, а `runlog` пришлёт уведомление о сбое.
4. **SMB: разделение cleanup и Close.** `cleanup()` закрывает только fs/session/conn. Контекст монитора отменяет только `Close()`. Отдельный «контекст попытки» не нужен: `connect` и так берёт ctx монитора.
5. **SMB: seam для тестов.** Поле `fs` получает тип неэкспортируемого интерфейса `share{WriteFile, Stat, Umount}`, которому удовлетворяет `*smb2.Share`. `write` переходит на `fs.WriteFile`. При `fs == nil` возвращается ошибка `smb not connected`, и `retry.Do` её повторяет. Альтернатива — подменяемая функция записи; это тестовый крючок в продакшен-коде, интерфейс чище.
6. **MAX: seam для тестов.** У `maxcli.NewApi` есть опция `WithBaseURL`, поэтому тесты поднимают `httptest.Server`, а продакшен-код не меняется.

## Risks / Trade-offs

- [Запуск с одним получателем MAX, у которого потерялось вложение, получит `failed`, хотя часть ушла] → Это осознанный выбор: `delivered` считает только полностью доставленных получателей, а уведомление о сбое важнее точного статуса.
- [Гонка: монитор переписывает `smb.fs`, пока `Upload` его читает] → Существовала до ветки, в коде отмечается `shortcut:`; исправить мьютексом, если гонку поймает `-race` или прод.
- [`WriteFile` создаёт файл с `O_TRUNC`, как и текущий `Create`] → Поведение не меняется.

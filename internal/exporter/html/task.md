# Техническое задание: универсальный Grid Layout Engine для HTML/PDF-отчётов

## 1. Цель

Необходимо реализовать универсальный механизм размещения элементов отчёта на фиксированной A4-странице.

На первом этапе элементами являются:

* `chart` — график;
* `table` — таблица.

В дальнейшем механизм должен позволять без изменения layout engine добавлять:

* `metric`;
* `text`;
* `image`;
* другие типы блоков.

Layout должен поддерживать:

1. автоматическое размещение блоков;
2. ручное указание ширины блока;
3. ручное указание высоты блока;
4. автоматический расчёт высоты там, где она не задана;
5. размещение нескольких элементов в одну строку;
6. вертикальное размещение;
7. перенос блока на следующую A4-страницу;
8. предсказуемое поведение без переполнения страницы;
9. отсутствие необходимости вручную указывать `x`/`y` в шаблонах;
10. возможность последующего расширения до полноценного dashboard-like layout, аналогичного по концепции Metabase.

---
 # 2. Основной принцип

Layout не должен быть частью конкретного элемента.

`chart`, `table`, `metric` и другие компоненты отвечают только за:

* подготовку данных;
* HTML содержимого;
* предпочтительный размер;
* возможность разбиения на несколько страниц.

Отдельный `layout engine` отвечает за:

* поиск свободного места;
* вычисление `x`;
* вычисление `y`;
* перенос на следующую страницу;
* резервирование ячеек;
* проверку выхода за границы страницы.

То есть:

```text
Template
   ↓
ReportBlock
   ↓
Layout Engine
   ↓
PositionedBlock
   ↓
HTML/CSS
   ↓
Chromium
   ↓
PDF
```

---

# 3. Grid страницы

Для каждой страницы использовать фиксированную сетку:

```text
12 колонок × N строк
```

Количество колонок фиксированно:

```go
const GridColumns = 12
```

Количество строк также должно быть фиксированным внутри layout engine.

Рекомендуемое начальное значение:

```go
const GridRows = 12
```

При необходимости это значение должно быть вынесено в конфигурацию.

---

# 4. Почему используется 12 колонок

12 колонок позволяют естественно представлять наиболее частые размеры:

```text
12 = 100%
6  = 50%
4  = 33.33%
3  = 25%
2  = 16.67%
1  = 8.33%
```

Таким образом:

```text
w=12
```

означает блок на всю ширину.

```text
w=6
```

означает половину строки.

```text
w=4
```

означает треть строки.

```text
w=3
```

означает четверть строки.

---

# 5. Размер блока

Каждый блок должен иметь размер:

```go
type BlockSize struct {
    W int
    H int
}
```

Где:

* `W` — количество колонок;
* `H` — количество вертикальных grid-ячеек.

Пользователь может указывать `W` и `H`.

Оба параметра являются **опциональными**.

---

# 6. Значения по умолчанию

Каждый тип элемента должен иметь собственный размер по умолчанию.

Начальные значения:

```text
chart:
    W = 6
    H = 4

metric:
    W = 3
    H = 2

table:
    W = 12
    H = auto

text:
    W = 12
    H = auto
```

Эти значения не должны быть зашиты в layout engine.

Каждый тип компонента должен самостоятельно возвращать свои default dimensions.

---

# 7. Ручное переопределение размера

Пользователь должен иметь возможность задавать:

```gotemplate
(chartOptions
    "w" 6
    "h" 4
)
```

Параметры:

```text
w — ширина в grid-колонках
h — высота в grid-строках
```

Примеры:

### Половина страницы

```gotemplate
"w" 6
```

### Вся ширина

```gotemplate
"w" 12
```

### Четверть страницы

```gotemplate
"w" 3
```

### Половина ширины и большая высота

```gotemplate
"w" 6
"h" 6
```

Если параметр не указан, используется default/auto значение компонента.

---

# 8. Ограничения размеров

`w` должен удовлетворять:

```text
1 <= w <= 12
```

`h` должен удовлетворять:

```text
h >= 1
```

Значения:

```text
w = 0
w > 12
h = 0
h < 0
```

должны приводить к ошибке template/rendering.

Ошибка должна содержать имя компонента и проблемный параметр.

Пример:

```text
chart: option "w" must be between 1 and 12
```

---

# 9. Координаты X/Y

Пользователь **не должен обязан указывать `x` и `y`**.

Layout engine должен вычислять их автоматически.

Внутренне каждый размещённый блок должен иметь:

```go
type GridPosition struct {
    X int
    Y int
}
```

При этом:

```text
X = колонка
Y = строка
```

Их можно использовать внутри renderer:

```css
grid-column: ...
grid-row: ...
```

Но они не должны быть обязательной частью template API.

---

# 10. Алгоритм автоматического размещения

Необходимо реализовать first-fit / row-major placement.

Алгоритм:

```text
1. Берём блок.
2. Получаем его W/H.
3. Начинаем поиск с верхнего левого угла страницы.
4. Проверяем позиции слева направо.
5. После окончания строки переходим на следующую строку.
6. На первой свободной позиции размещаем блок.
7. Резервируем его ячейки.
8. Переходим к следующему блоку.
```

Пример:

```text
Grid = 12 × 12

Block 1 = 6 × 4
Block 2 = 6 × 4
Block 3 = 4 × 4
Block 4 = 4 × 4
Block 5 = 4 × 4
```

Результат:

```text
┌───────────────┬───────────────┐
│               │               │
│   Block 1     │   Block 2     │
│      6×4      │      6×4      │
│               │               │
├───────┬───────┬───────┐
│ B3    │ B4    │ B5    │
│ 4×4   │ 4×4   │ 4×4   │
└───────┴───────┴───────┘
```

---

# 11. Размещение должно учитывать фактическую занятость

Нельзя просто размещать блоки последовательно по строкам.

Layout engine должен поддерживать occupancy map:

```go
type Grid struct {
    Columns int
    Rows    int

    occupied [][]bool
}
```

Проверка:

```go
func (g *Grid) CanPlace(
    x int,
    y int,
    w int,
    h int,
) bool
```

Должна проверять:

1. выход за правую границу;
2. выход за нижнюю границу;
3. пересечение с уже размещёнными блоками.

---

# 12. Новая страница

Если блок невозможно разместить на текущей странице, необходимо:

1. завершить текущую страницу;
2. создать новую grid;
3. разместить блок на новой странице с позиции `0,0`.

Пример:

```text
Page 1:

┌───────────────────────┐
│ chart 6×4 │ chart 6×4 │
├───────────┴───────────┤
│ table 12×5            │
└───────────────────────┘


Page 2:

┌───────────────────────┐
│ metric                │
└───────────────────────┘
```

---

# 13. Нельзя допускать переполнения страницы

Layout engine должен гарантировать:

```text
x + w <= GridColumns
y + h <= GridRows
```

Если блок не помещается, он переносится на следующую страницу.

Нельзя надеяться на то, что Chromium сам корректно перенесёт блок.

Это особенно важно для PDF.

---

# 14. Высота графиков

У графика должна остаться возможность задавать физическую высоту Chart.js:

```gotemplate
"height" 300
```

Но эта высота и grid `H` — разные понятия.

Например:

```text
"h"      = 4 grid rows
"height" = 300px
```

`h` определяет место блока на странице.

`height` определяет размер самого Chart.js canvas.

То есть:

```text
Grid Layout
    ↓
определяет место блока

Chart height
    ↓
определяет внутренний размер графика
```

Они не должны смешиваться.

---

# 15. Таблицы

Для таблицы ширина должна задаваться аналогично:

```gotemplate
(tableOptions
    "w" 8
)
```

Высота таблицы по умолчанию должна рассчитываться автоматически.

Например:

```text
ширина = 12
количество строк = 18
```

layout adapter таблицы должен вычислить её предпочтительную высоту.

У таблицы должна быть возможность задать:

```gotemplate
(tableOptions
    "w" 8
    "h" 6
)
```

Если `h` задан вручную — использовать его.

Если `h` не задан — использовать автоматический расчёт.

---

# 16. Таблица должна поддерживать разбиение

В отличие от графика, таблица является `splittable` block.

Например:

```text
Table:
40 строк
```

Если на текущей странице помещается только 20 строк:

```text
Page 1:
rows 1–20

Page 2:
rows 21–40
```

Необходимо предусмотреть интерфейс:

```go
type Block interface {
    Size() BlockSize

    Render() template.HTML

    Splittable() bool
}
```

Для таблицы дополнительно потребуется механизм:

```go
Split(availableHeight int) (current, remainder Block, ok bool)
```

Для chart:

```go
Splittable() == false
```

---

# 17. Поведение несортируемых блоков

Для элементов:

```text
chart
metric
image
```

если элемент целиком не помещается на текущей странице, он не должен разрываться.

Он переносится целиком.

---

# 18. CSS Grid

CSS должен отображать уже рассчитанную Go-позицию.

Для страницы:

```css
.report-grid {
    display: grid;

    grid-template-columns:
        repeat(12, minmax(0, 1fr));

    grid-template-rows:
        repeat(12, minmax(0, 1fr));

    gap: 4mm;

    width: 100%;
    height: 230mm;
}
```

Каждый элемент:

```css
.report-grid-item {
    min-width: 0;
    min-height: 0;

    overflow: hidden;

    break-inside: avoid;
    page-break-inside: avoid;
}
```

---

# 19. Позиционирование элемента

Renderer должен генерировать:

```html
<div
    class="report-grid-item"
    style="
        grid-column: 1 / span 6;
        grid-row: 1 / span 4;
    "
>
    ...
</div>
```

Внутри:

```text
grid-column = X + 1
grid-row    = Y + 1
```

Потому что CSS Grid использует индексацию с 1, а внутренний Go layout — с 0.

---

# 20. A4 page

Каждая страница должна генерироваться как отдельный контейнер:

```html
<div class="report-page">

    <div class="report-grid">

        ...

    </div>

</div>
```

CSS:

```css
.report-page {
    width: 210mm;
    height: 297mm;

    box-sizing: border-box;

    position: relative;

    page-break-after: always;
    break-after: page;

    overflow: hidden;
}

.report-page:last-child {
    page-break-after: auto;
    break-after: auto;
}
```

Нельзя позволять grid выйти за пределы `.report-page`.

---

# 21. Размер рабочей области A4

Исходный `.page` уже использует:

```css
width: 210mm;
min-height: 297mm;
padding: 16mm 15mm;
```

и footer располагается с `bottom: 9mm`. Эти параметры существуют в текущем шаблоне и должны учитываться при расчёте доступной области.
Необходимо вынести параметры страницы в конфигурацию:

```go
type PageLayout struct {
    Width  int
    Height int

    PaddingTop    int
    PaddingRight  int
    PaddingBottom int
    PaddingLeft   int

    HeaderHeight int
    FooterHeight int
}
```

Единица измерения может быть `mm`.

---

# 22. Важное разделение физического и логического размера

Необходимо различать:

### Logical grid

```text
12 × 12
```

### Physical page

```text
210 × 297 mm
```

### Block

```text
6 × 4 grid cells
```

### Inner chart

```text
300 px
```

Layout engine работает только с логическими grid units.

Renderer переводит результат в CSS.

# 23. Template API

Необходимо сохранить существующий:

```go
chart(...)
```

и `chartOptions(...)`, уже используемый текущей системой. В текущем коде `chartOptions` принимает произвольные пары key/value и возвращает `map[string]any`, поэтому размеры логично расширить именно через эту существующую точку входа.

Пример:

```gotemplate
{{ chart
    "bar"
    (dataset . "data")
    "date"
    (chartList "count:Количество")
    (chartOptions
        "title" "Переводы"
        "w" 6
        "h" 4
        "height" 300
    )
}}
```

---

# 24. Необходимый новый API

Добавить общий тип:

```go
type ReportBlock struct {
    Type string

    Content template.HTML

    Size BlockSize

    ExplicitWidth  bool
    ExplicitHeight bool

    Splittable bool
}
```

Позиция:

```go
type GridPosition struct {
    X int
    Y int
}
```

Размещение:

```go
type PositionedBlock struct {
    ReportBlock

    Position GridPosition

    Page int
}
```

Grid:

```go
type Grid struct {
    Columns int
    Rows    int

    occupied [][]bool
}
```

---

# 25. Layout engine

Основной интерфейс:

```go
type LayoutEngine interface {
    Layout(blocks []ReportBlock) ([]Page, error)
}
```

Страница:

```go
type Page struct {
    Blocks []PositionedBlock
}
```

Алгоритм `Layout()`:

```text
создать Page 1

для каждого block:

    получить размер block

    если block можно разместить:
        разместить
        continue

    если block splittable:
        попытаться разделить
        текущую часть разместить
        остаток обработать дальше

    иначе:
        создать новую страницу
        разместить block целиком
```

---

# 26. Автоматические размеры

Для каждого блока должен быть механизм:

```go
PreferredSize() BlockSize
```

Пример chart:

```go
func (c ChartBlock) PreferredSize() BlockSize {
    return BlockSize{
        W: 6,
        H: 4,
    }
}
```

Если пользователь указал:

```text
w=12
```

получаем:

```text
W = 12
H = 4
```

Если:

```text
h=6
```

получаем:

```text
W = 6
H = 6
```

---

# 27. Порядок приоритетов размеров

Использовать следующий порядок:

```text
1. Явно заданное пользователем значение
2. Автоматически вычисленное значение компонента
3. Default value компонента
```

Например:

```text
chart default W = 6
chart default H = 4

user:
w = 12
```

результат:

```text
W = 12
H = 4
```

---

# 28. Никаких `x/y` в обычном API

Не реализовывать обязательный API вида:

```gotemplate
"x" 4
"y" 8
```

на первом этапе.

Layout должен быть максимально декларативным:

```gotemplate
chart(w=6,h=4)
chart(w=6,h=4)
table(w=12)
```

И сам искать место.

При этом внутренние `X/Y` обязательно должны существовать в модели, поскольку они нужны renderer.

---

# 29. Если в будущем потребуется ручное позиционирование

Архитектура должна позволять позже добавить:

```gotemplate
"x" 6
"y" 4
```

без изменения модели `Grid`.

Но реализацию пользовательских `x/y` сейчас можно не делать.

# 30. Использование в шаблоне

Предпочтительный итоговый API:

```gotemplate
{{ reportGrid }}

    {{ chart
        "bar"
        ...
        (chartOptions
            "w" 6
            "h" 4
        )
    }}

    {{ chart
        "line"
        ...
        (chartOptions
            "w" 6
            "h" 4
        )
    }}

    {{ table
        ...
        (tableOptions
            "w" 12
        )
    }}

{{ endReportGrid }}
```

Но конкретная реализация `reportGrid/endReportGrid` может быть адаптирована к существующему template engine.

Ключевое требование: **все блоки должны поступать в единый layout engine до финального формирования HTML страницы.**

Текущие `.chart-card`, `.chart-card-title` и `.report-chart` сохранить, но сделать их внутренними компонентами блока. В текущем коде эти стили уже определены в `styles()`.

# 32. Chart renderer

`renderChart()` не должен создавать `.report-grid`.

Он должен отвечать только за:

```text
chart-card
chart-card-title
report-chart
canvas
script Chart.js
```

## В текущем коде `renderChart()` уже содержит всю эту логику генерации Chart.js config и canvas; её нужно сохранить, а layout-обёртку вынести наружу.

# 33. Не смешивать `height` и grid `H`

Например:

```gotemplate
(chartOptions
    "w" 6
    "h" 4
    "height" 300
)
```

означает:

```text
w      = 6 grid columns
h      = 4 grid rows
height = 300 CSS pixels
```

Это три разных уровня:

```text
w/h
    ↓
layout

height
    ↓
Chart.js canvas
```

---

# 34. Заполнение свободного места

Layout engine не должен пытаться искусственно растянуть блок до оставшегося места.

Если блок имеет:

```text
W=4
H=4
```

он занимает ровно:

```text
4 × 4
```

Оставшееся пространство остаётся свободным.

Это позволяет пользователю контролировать композицию.

---

# 35. Перенос на новую страницу

Если свободного места недостаточно:

```text
Page 1:
free cells < block size
```

блок переносится на:

```text
Page 2:
x=0
y=0
```

Если блок `splittable=false`.

---

# 36. Требования к table

Для таблицы:

```text
W — пользователь задаёт
H — вычисляется автоматически
```

Например:

```gotemplate
(tableOptions "w" 6)
```

означает:

```text
ширина = 50%
высота = автоматически
```

При этом renderer обязан предоставить layout engine информацию о предполагаемой высоте таблицы **до** формирования окончательной страницы.

---

# 37. Таблица должна иметь ограничение высоты

Если таблица большая, она не должна растягивать `.report-page`.

Она должна быть разбита на части.

Каждая часть должна повторять header таблицы:

```text
Page 1
┌──────────────────────┐
│ A │ B │ C │ D       │
├──────────────────────┤
│ ...                  │
└──────────────────────┘

Page 2
┌──────────────────────┐
│ A │ B │ C │ D       │
├──────────────────────┤
│ ...                  │
└──────────────────────┘
```

---

# 38. Запрет на CSS-only pagination

Нельзя использовать как основной механизм:

```css
break-inside: auto;
```

для решения layout.

CSS должен получать уже рассчитанные страницы.

Допустимо использовать:

```css
break-inside: avoid;
page-break-inside: avoid;
```

как дополнительную защиту.

# 40. Что не требуется на первом этапе

Не реализовывать:

* drag-and-drop;
* визуальный редактор;
* пользовательские `x/y`;
* CSS auto-placement вместо Go layout;
* responsive layout под произвольные экраны;
* горизонтальный overflow;
* автоматическое масштабирование блоков;
* автоматическое изменение размеров уже размещённых блоков.

Главная цель первого этапа — **детерминированная серверная раскладка для A4 PDF**.

# 41. Ожидаемый результат архитектуры

В результате должна получиться структура:

```text
Template
    │
    ├── chart(...)
    ├── table(...)
    ├── metric(...)
    └── text(...)
            │
            ▼
      []ReportBlock
            │
            ▼
       Layout Engine
            │
            ├── Page 1
            │    ├── Block
            │    ├── Block
            │    └── Block
            │
            ├── Page 2
            │    ├── Block
            │    └── Block
            │
            ▼
      HTML Renderer
            │
            ▼
         Chromium
            │
            ▼
           PDF
```

Основной архитектурный принцип: **компоненты не должны знать, где они находятся на странице; layout engine не должен знать внутренности компонента**.

Это позволит позже без изменения механизма размещения добавить таблицы, KPI, текстовые блоки и другие элементы.
